# START HERE

Welcome to the Sports RAG project.

This repository follows a documentation-first development workflow. Before implementing, modifying, or proposing any change, you must understand the project through its documentation.

Do **not** start by reading the source code.

Instead, follow the steps below exactly.

---

# Step 1 — Read the development rules

Read:

- `CODEX.md`

This document defines:

- how you should collaborate on this project;
- the expected development workflow;
- documentation responsibilities;
- engineering standards.

After reading it, continue to the next step.

---

# Step 2 — Read the project documentation

Read the following documents in exactly this order:

1. `README.md`
2. `docs/project-history/00-project-history.md`
3. `docs/learning/learning-philosophy.md`
4. `docs/architecture/architecture.md`
5. `docs/architecture/folder-structure.md`
6. `docs/architecture/data-flow.md`
7. `docs/development/project-state.md`
8. `docs/development/roadmap.md`
9. Every document inside `docs/decisions/`

Do not skip documents.

---

# Step 3 — Confirm your understanding

Before writing any code, provide a concise summary covering:

- the purpose of the project;
- the current architecture;
- the main data flows;
- the responsibilities of each architectural layer;
- the architectural decisions recorded in the ADRs;
- the current implementation status;
- the next milestone in the roadmap.

If you find inconsistencies between documents, list them before continuing.

Do not begin implementation until this summary has been provided.

---

# Step 4 — Wait for instructions

After confirming your understanding, wait for the next user request.

Do not proactively implement features.

Do not modify the architecture.

Do not update documentation.

Only continue after receiving a specific task.

---

# During Development

For every implementation:

1. Understand the requested feature.
2. Explain the architectural impact.
3. If multiple valid solutions exist, explain the alternatives and wait for the developer's decision.
4. Divide the implementation into small steps.
5. Implement one step at a time.
6. Suggest the required documentation updates.
7. Suggest a commit message.

Never skip documentation when it is affected by a change.

---

# Project Goal

Remember that Sports RAG is primarily a learning project.

Understanding the architecture and the reasoning behind every decision is more important than implementing features quickly.

Whenever there is a conflict between implementation speed and learning value, prioritize learning.
